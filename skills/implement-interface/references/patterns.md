# 模式参考

常规是 `setter` / `getter`。槽位存取说不清的行为，才立 `Contract-Action`。

## `setter` / `getter` 单向依赖

槽本身就是契约：写入只改该槽，读出无副作用。不成对也可以。

| 场景     | 形态
| ---      | ---
| 名称     | `setter` / `getter` 身份的名称                |
| 使能     | `setter` / `getter` 一个布尔槽                |
| 容量     | `setter` / `getter` 上限                      |
| 阈值     | `setter` / `getter` 标量界限                  |
| 时限     | `setter` / `getter` 一个时间点或期限          |
| 当前选中 | `setter` / `getter` 当前身份                  |
| 绑定槽   | `setter` 写入句柄，`getter` 读出；空 = 未绑定 |
| 分类标签 | `setter` / `getter` 离散标签                  |
| 只读槽   | 仅 `getter`（占用、派生前的已存快照）         |
| 只写槽   | 仅 `setter`（注入后不再从同一槽读出）         |

## 事件驱动型接口形态

事件驱动型系统的组件通信依赖于事件异步派发，公开契约是「接受 / 投出哪一种事件」，不是同步把对方内部步骤跑完。配置仍可以是 `setter` / `getter`；往来不走槽位存取。
一般情况下通信对象的事件类型契约是暴露出来的。

| 场景     | 形态                                              |
| ---      | ---                                               |
| 投递     | 只把事件交给派发，不等待对方履约结束              |
| 接收     | 一个入口按事件身份履约，不把分派表暴露给调用方    |
| 信号     | 无载荷，事件身份即契约                            |
| 带载荷   | 身份 + 载荷形状即契约；载荷不是内部结构           |
| 订阅     | 登记「事件身份 → 处理动作」                       |
| 退订     | 撤销该登记                                        |
| 回告     | 结果用另一次事件；投递调用不返回业务值            |
| 配对往来 | 请求与应答靠事件身份配对，不靠调用方背时序        |
| 自投递   | 向自己投后续事件；不把队列当成可 `getter` 的槽    |
| 可忽略   | 契约写明可不处理的身份；不是静默发明新事件        |

## Contract-Action -- 特殊的反向依赖接口设计

反向依赖和运行时注入，通常用在需要避免循环依赖的情景：有需求的一方声明所需契约，对端只提供实现；实现者不拥有接口；源码依赖指向契约，不指向对端具体形态。接线在环外、在运行时注入。

| 场景       | 形态                                                |
| ---        | ---                                                 |
| 所需契约   | 由需要的一方声明并拥有；对端只实现，不拥有          |
| 所供实现   | 满足所需契约的具体动作；调用方只依赖契约            |
| 注入槽     | `setter` / 只写槽写入实现句柄；空 = 尚未接线        |
| 环外接线   | 第三者在运行时注入；环内两边互不引对方具体形态      |
| 互需拆环   | 抽出一侧所需契约再注入另一侧，不要两边互引          |
| 回调       | 回调是所需契约，不是对端把内部入口借过来            |
| 事件订阅   | 订阅登记也可作注入：登记的是契约动作，不是对端类型  |
| 可替换     | 同一所需契约可注入不同实现；公开形状不变            |
| 未注入     | 公开操作要求已接线；未注入不是业务失败，是形态未成  |
