# Zoom Out

## Goal

我们要以顶层包/模块抽象层级对系统的生态层级进行边界定位，以 UML 序列图（sequence-diagram）为表达元素承载系统交互契约边界抽象。

这个 skill 的核心是**提供一个视角**：当讨论在细节里打转时，借包/模块级抽象把问题重新摆一遍，为用户提供思路、轮廓与关键细节。它不是项目架构的现状还原——讨论的对象可以是尚未存在的设计、一个构想、或某个局部决策的全局影响。

## When to Use

- 讨论陷入类/函数级实现细节，需要抬升抽象层级重新看问题。
- 一个设计决策拿不准，想看看它在顶层交互图景里的位置与影响。
- 脑子里已有模糊图景，想找人对一遍思路是否自洽。

## When NOT to Use

- 需要展开某个模块的内部结构设计 → 转 `uml-composing`。
- 交互意图已确定，只需编写/修复 PlantUML 语法 → 转 `plantuml-master`。

## How to Engage

- **视角服务于讨论**。包/模块抽象是讨论问题的工具，不是必须填满的框架。能照亮当前问题的那部分就谈那部分，其余留白。
- **讨论先行，图为佐证**。序列图是讨论的投影，用于检验思路是否成立；轮廓未成时不出图，不为出图而出图。
- **一次一个焦点**。沿设计树逐分支展开，每轮只追一个问题，并给出你的倾向性判断与依据，供用户拍板，而不是罗列开放式问题。
- **主动供料**。持续提供：从这个视角看到的候选边界、值得注意的交互对、被细节藏起来的耦合与风险。用户要的是"帮我看到我没看到的"，不是被审问。
- **守住尺度**。话题滑向某个模块内部时，记下它，拉回顶层，并提示可转 `uml-composing` 深入。

## 边界与序列图的评判标准

1. 定位包/模块范围时以交互边界契约稳定、契约能映射系统实际交互抽象为评判标准。
2. 序列图（sequence-diagram）的生命线/参与者为包/模块抽象主体，交互行为映射系统的实际交互契约。需要落 PlantUML 语法时交 `plantuml-master`。

## What the User Gets

讨论到哪一层，就给到哪一层，不强制完整交付：

- 一个顶层观察角度：当前问题在包/模块图景里被重新摆出来的样子。
- 交互思路：关键交互对、方向、取舍的探讨。
- 关键细节：被忽略的路径、隐藏的耦合、值得追问的点。
- 未决问题：讨论中浮现但尚无结论的边界归属或交互，逐条列出。
- 序列图：仅当讨论成熟、用户认为值得落图时才产出。
